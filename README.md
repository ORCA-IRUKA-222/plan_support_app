# 企画伴走 — 立案から企画書発表までをサポートするアプリ

種出しから核の一行化、骨格の検証、企画書、発表リハーサルまでを**段階（フェーズ）とゲート**で進めるアプリです。
PC のブラウザと Android スマホの両方で使えて、同じ内容が同期されます。

**そのまま開く: <https://orca-iruka-222.github.io/plan_support_app/>**
（インストールもサーバーの起動も不要。PC・スマホどちらもこの URL で使えます）

- **ローカルファースト**: データはまず端末内に保存され、通信が切れても入力を続けられます。
  上の URL か APK なら、**電波が無くても起動できます**
  （LAN 経由の `http://192.168.x.x` だけはブラウザの制約で不可。[理由](docs/PWA-vs-APK.md)）。
- **同期は GitHub Gist**: 非公開の Gist を1つ使って PC とスマホを揃えます。サーバーの常時起動は不要で、外出先からでも同期できます。
- **PWA / APK の両対応**: ブラウザからそのままインストールでき、Capacitor で APK も作れます。

## 1. できること

### 進行（5段階 + ゲート）

企画書作りは「書く作業」ではなく「収束させる作業」です。段階ごとに、次へ進んでいい条件（ゲート）を
決めておくと手戻りが減ります。アプリは各ゲートを**できる範囲で自動判定**し、残りをチェックリストにします。

| 段階 | 画面 | やること | 次へ進む条件 |
|---|---|---|---|
| 0. 素材ストック | ネタ帳 | 遊んだもの・違和感・数字をメモに溜める | ネタ帳が枯れていない |
| 1. 種を出す | 種出し | 発散。質を問わず30〜50個 | 人に話したくなる種が3つ以上 |
| 2. 核を決める | 核を決める | 1行に圧縮。3層モデルの「核」を確定 | 一文で言えて、聞いた人が絵を想像できる |
| 3. 骨格を検証 | 骨格を検証 | コアループ・ターゲット・収益・実現性 | 引き算テストと一般化テストを通過 |
| 4. 書面化 | 企画書 | 構成・図・数値・演出 | 冒頭30秒で「面白そう」と思わせられる |

例えば「種が30個以上あるか」「★が3つ以上あるか」「出所7分類のうち4種類以上から出したか」
「核が60字以内か」「4判定すべてが3以上か」「目的に数値が入っているか」は、
入力内容から自動で判定されます。ダッシュボードには**次にやること**が1つだけ表示されます。

### 道具

- **思考ツール**: それぞれ手法本来の図として操作します。入力欄が並ぶだけの画面ではありません。

  | ツール | 画面 |
  |---|---|
  | マインドマップ | 中心の種から8軸が放射状に伸び、枝を足すと線でつながる。枝どうしを結ぶと点線が引かれる |
  | 三角メモ | 左右に三角形が2つ。A・Bの言葉が三角の中に並び、1つずつ選んで掛け合わせる |
  | マンダラート | 9×9＝81マスの格子。中央3×3が核＋8テーマ、周囲8ブロックが各テーマの展開 |
  | SCAMPER | 対象を中心に7操作を輪状に配置。Eliminate と Reverse を色で強調 |
  | 逆転発想 | 「常識」と「逆にしたら」を ⇄ で向かい合わせ、下に成立条件 |
  | 問題逆転 | 5ステップを番号付きの縦フローで表示 |
  | アナロジー移植 | 表層（捨てる）→ 構造（抜く）→ 移植先 の3列を矢印でつなぐ |
  | 体験の時間割 | 目盛り付きの折れ線グラフ。点を押すとその時点を編集できる |
  | KJ法 | 付箋を束として表示。選んでまとめ、あとから名前を付ける（「種出し」画面内） |

  図は狭い画面では横スクロールで全体を見られます。編集は図の下のパネルで行うので、
  スマホでも入力しやすいようにしてあります。
- **フレームワーク**: 3C分析／SWOT分析／6W2H／CTPT／書く前に潰す5つの質問。
- **企画書**: 6つの必須セクション + 弱点セクション。フレームワークに書いた内容から**下書きを自動生成**できます。
  Markdown / HTML の書き出しと、ブラウザ印刷からの PDF 化に対応。
- **発表**: 企画書からスライドを組み立て、冒頭30秒のフック・リハーサル用タイマー・想定質問を扱います。

### 設計上の意図

- マインドマップは自由に枝を伸ばすより**第1階層を8軸に固定**したほうが機能します。
  第2階層が空の軸と、まったく手つかずの軸は**弱点として赤く表示**されます。
- 「操作」と「収益」のように、**枝から枝への線**を引けます。
- KJ法は先にカテゴリを決めず、集めてから名前を付ける順番でしか操作できません。
- 弱点は1つ残して「それでもやる理由」を書く欄があります。全部潰した企画書は安全ですが面白くないためです。

### いちばん簡単な使い方（インストール不要）

PC でもスマホでも、ブラウザで次を開くだけです。

https://nodejs.org/ja から LTS 版を入れてください。入ったかどうかは次で確認できます。


コマンドは**このリポジトリのフォルダの中**（`package.json` がある場所）で実行します。
まだ PC にコードがなければ、どちらかの方法で取得してください。

```bash

git clone https://github.com/ORCA-IRUKA-222/plan_support_app.git
cd plan_support_app
```

方法B: git を使わない場合は、GitHub のリポジトリ画面で緑の **Code** ボタン →
**Download ZIP**。展開してできたフォルダに移動します。

```bash

cd ~/Downloads/plan_support_app-main                          # macOS の例
```

正しい場所にいるかは、`package.json` が見えるかで確認できます。

```bash
dir package.json     # Windows (PowerShell / コマンドプロンプト)
ls package.json      # macOS / Linux
```

### フォルダの場所が分からなくなったら

**PC のどこに置いたか忘れた場合**は、次のコマンドで探せます。

```powershell
# Windows (PowerShell)

  Select-Object -First 5 FullName
```


見つかったパスに `cd` すれば、そこが作業フォルダです。
`git clone` をそのまま実行した場合は、ターミナルを開いたときの場所に作られています。
Windows なら `C:\Users\<ユーザー名>\plan_support_app` のことが多いです。

**エクスプローラーから開く方法**もあります。フォルダを開いた状態で、
アドレスバーに `powershell` と入力して Enter を押すと、その場所でターミナルが開きます。

そこが目的のフォルダかどうかは、次で確かめられます。

```bash

```

### 最新にする（2回目以降）

> GitHub Pages（上の URL）で使っている場合、更新は自動で反映されるので
> この節は不要です。表示が古いときだけ **Ctrl + Shift + R**。

**`git pull` を忘れると、いくら `npm run build` しても画面は変わりません。**

```bash

```

画面が変わらないときはブラウザで **Ctrl + Shift + R**（強制再読み込み）を押してください。

ZIP でダウンロードした場合は `git pull` が使えないので、
もう一度 **Code → Download ZIP** から取り直してください。

### どこからでも開けるようにする（任意・GitHub Pages）

同期を Gist に移したことで、このアプリは**静的ファイルだけで完結**します。
GitHub Pages に置けば、PC でサーバーを動かさなくてもスマホから開けます。
**HTTPS になるので PWA のオフライン起動も効くようになります**（後述の制約が消えます）。

`main` に push すると `.github/workflows/pages.yml` が自動で公開します。

公開先: **<https://orca-iruka-222.github.io/plan_support_app/>**

**最初に1回だけ、配信元の設定が必要です。**
[Settings → Pages](https://github.com/ORCA-IRUKA-222/plan_support_app/settings/pages) を開き、
**Build and deployment → Source** を **GitHub Actions** にしてください。
（この設定だけはワークフローから変更できません。`GITHUB_TOKEN` では
`PUT /repos/:owner/:repo/pages` が 403 になるためです。）

> - プライベートリポジトリの Pages は有料プランが必要です。無料プランなら public にしてください
>   （入力したデータは Gist と各端末にあり、リポジトリには入りません）
> - 反映には push から1〜2分かかります。表示が古いときは **Ctrl + Shift + R**
> - アプリではなく **README が表示される**場合は、上の設定が「Deploy from a branch」の
>   ままです。この状態だと同じ push で Jekyll のビルド
>   （Actions タブの *pages build and deployment*）も走り、**あとから終わったほうが勝つ**ため、
>   アプリを配信しても README で上書きされます。
>   ワークフローは毎回この状態を検査して、実行ログと実行サマリーに赤いエラーを出します
> - 設定を直したあとは、Actions タブ → *Deploy to GitHub Pages* → **Run workflow** を
>   一度実行すると、すぐに反映されます

### Android スマホで使う

2つの入れ方があります。違いは [docs/PWA-vs-APK.md](docs/PWA-vs-APK.md) にまとめました。
ざっくり言うと **どちらもホーム画面のアイコンから全画面で開く点は同じ**で、
違うのは配り方（PWA はサーバー経由、APK はファイルを直接インストール）です。

**方法A: PWA としてインストール（おすすめ・PC 不要）**

スマホの Chrome で **<https://orca-iruka-222.github.io/plan_support_app/>** を開き、
右上のメニューから「アプリをインストール」を選びます。
**HTTPS なので Service Worker が動き、電波が無くても起動できます。**
PC を立ち上げる必要はありません。

> LAN サーバー（`npm run server` → `http://<PCのIP>:8787`）からでも入れられますが、
> **そちらは PC を切るとスマホから開けません。** オフライン起動に必要な
> Service Worker は HTTPS か localhost でしか動かず、`http://192.168.x.x` は
> どちらでもないためです（アプリの「設定・同期」画面の先頭に可否が出ます）。
>
> データの同期そのものは GitHub Gist 経由なので、どの開き方でも同じように揃います。

**方法B: APK を作る（PCを起動していない場所でも単独で使いたいとき）**

Capacitor で APK を生成します。JDK 21 と Android SDK が必要です。

> APK は GitHub Gist（HTTPS）と通信するので、特別な設定は要りません。
> 平文 HTTP の LAN サーバーにもつなげるよう `allowMixedContent` と
> `usesCleartextTraffic` は有効にしてありますが、Gist 同期では使いません。

```bash
./scripts/build-apk.sh debug
# → app/android/app/build/outputs/apk/debug/app-debug.apk
```

Android SDK が手元にない場合は、GitHub Actions の **Android APK** ワークフローを
手動実行（Actions タブ → Android APK → Run workflow）すると、
実行結果の Artifacts から `kikaku-bansou-debug-apk` をダウンロードできます。
zip を展開すると `app-debug.apk` が入っているので、スマホに転送してタップすればインストールできます
（初回は「提供元不明のアプリ」の許可が必要です）。

> `app/android/` は `capacitor.config.ts` から再生成できるためリポジトリには含めていません。
> スクリプトが必要に応じて `npx cap add android` を実行します。

ビルド実績 (GitHub Actions, ubuntu-latest):
`app-debug.apk` 4.4MB / Gradle 2分7秒 / compileSdk 35 / minSdk 23 (Android 6.0 以降) /
アプリID `app.kikaku.bansou`。APK の中に `assets/public/` として画面一式が入るので、
インストール後はサーバーなしで単独起動できます。

## 3. 端末間の同期（GitHub Gist）

自前のサーバーは要りません。**非公開の Gist を1つ**作り、そこに読み書きして PC とスマホを揃えます。
PC の電源が入っていなくても、スマホから外出先で同期できます。

### しくみ

すべてのデータは `id` と `updatedAt` を持つ**レコード**として保存されます。同期のたびに次を行います。

1. Gist を読む
2. 手元の記録と突き合わせ、レコードごとに **`updatedAt` の新しい方**を残す（Last-Write-Wins）
3. 突き合わせた結果を手元に反映する
4. 結果が Gist と違っていれば、**全量**を書き戻す

全量を書き戻すので、**どちらの端末で足したものも消えません**。
同じ項目を2台で同時に直した場合だけ、あとから保存した方が残ります。

### トークンを用意する

1. <https://github.com/settings/tokens> を開く
2. **Generate new token → Generate new token (classic)** を選ぶ
   - **Fine-grained tokens は Gist に対応していません。** 必ず classic を使ってください
3. Note に分かる名前（例: `kikaku-bansou`）、Expiration は好みで
4. **Select scopes で `gist` だけ**にチェックして **Generate token**
5. 表示された `ghp_…` をコピー（**1回しか表示されません**）

### 1台目（PC）

アプリの **設定・同期 → 端末間の同期** を開いて入力します。

| 項目 | 入れる値 |
|---|---|
| アクセストークン | 手順5でコピーした `ghp_…` |
| Gist ID | **空のまま** |

**「いま同期する」**を押すと非公開の Gist が作られ、**Gist ID が自動で入ります**。
うまくいかないときは **「接続をテスト」**を押すと、トークンの誤りと権限不足を区別して教えてくれます。

### 2台目（スマホ）

| 項目 | 入れる値 |
|---|---|
| アクセストークン | 1台目と**同じ** `ghp_…` |
| Gist ID | 1台目に表示された ID |

入れて「いま同期する」を押すと、1台目の内容が入ってきます。
以降は起動時・画面復帰時・変更の30秒後・表示中は60秒ごとに自動で同期します。

### トークンの扱い

> - トークンは**その端末のブラウザ内にだけ**保存されます
> - **Gist に書き込むデータにもバックアップファイルにもトークンは含まれません**
>   （Gist にトークンが入ると GitHub が漏洩と判定し、トークンを自動で無効化します）。
>   万一混ざった場合は送信を中止する安全装置を入れ、テストで確認しています
> - 権限は **`gist` のみ**に絞ってください。リポジトリには一切アクセスできません
> - 共用の PC では同期を設定しないことをおすすめします
> - 作られる Gist は **secret（非公開）** ですが、URL を知っている人は閲覧できます

### うまくいかないとき

| 表示 | 原因と対処 |
|---|---|
| トークンが GitHub に認識されませんでした | `ghp_` から末尾まで全部コピーできているか、前後に空白が入っていないか、有効期限が切れていないか、Gist ID 欄と入れ違いになっていないかを確認 |
| gist 権限がありません（Fine-grained） | classic ではなく Fine-grained token を作っています。classic で作り直してください |
| gist 権限がありません（現在の権限: …） | classic ですが `gist` にチェックが入っていません。GitHub のトークン設定画面で追加してください |
| Gist が見つかりません | Gist ID が違うか削除されています。1台目で Gist ID を空にして同期し直すと作り直せます |

### サーバーを使わない同期

「設定・同期」の**バックアップ**から JSON を書き出し、別の端末で読み込めば移せます。

### データはどこにあるか / バックアップ

同じ内容が3か所に置かれます。1か所が消えても他から戻せます。

| 場所 | 実体 | 消えるとき |
|---|---|---|
| PC のブラウザ | localStorage | ブラウザの閲覧データ削除 |
| スマホ | localStorage（PWA）／アプリ内（APK） | アプリの削除、ストレージの消去 |
| GitHub Gist | 非公開の Gist 1つ | その Gist を削除したとき |

**Gist が実質のバックアップです。** 全端末の全レコードが入っているので、
スマホを機種変更しても、新しい端末にトークンと Gist ID を入れれば元に戻ります。
削除したものも墓標として90日間残るため、消しすぎた直後なら気づけます。

節目では「設定・同期」→ バックアップ →「書き出す（JSON）」で手元にも残しておくと安心です。
Gist の履歴からも過去の版に戻せます（Gist のページで Revisions を見る）。

## 4. 開発

```bash
npm run dev          # 開発サーバー
npm run typecheck    # TypeScript の型チェック
npm test             # フロントエンド (vitest) + サーバー・スクリプト (node:test)
npm run build        # 本番ビルド
npm run server       # 画面を配信する静的サーバー
npm run apk          # Android APK（要 Android SDK）
```

### 構成

```
app/                   フロントエンド (React 19 + TypeScript + Vite)
  src/domain/          型・知識ベース・既定値・ゲート判定
  src/store/           永続化・マージ・同期クライアント
  src/views/           画面（進行5段階 + 思考ツール + フレームワーク）
  src/lib/             ID・時刻・書き出し
server/                画面を配信する静的サーバー（依存パッケージ0件）
scripts/build-apk.sh   APK ビルド
```

`app/src/domain/knowledge.ts` に、7分類・4判定・8軸・5つの質問・企画書の構成・
見やすさの法則などの**文言がすべて集約**されています。ここを直せばアプリ全体の表示が変わります。

## 6. 動作確認

```bash
npm test                              # 単体テスト（フロントエンド + サーバー + スクリプト）

npm run build && npm run server &     # 通し確認の前にサーバーを起動
npm run e2e                           # 画面を一通り操作して壊れていないか確認
npm run e2e:sync                      # 2端末が Gist 越しに揃うか確認
```

`npm run e2e` は実ブラウザで24項目を操作し、各ステップ後に画面が空になっていないかを確認します
（型チェックでは見つからない実行時の壊れ方を拾うため）。
`npm run e2e:sync` は localStorage を分けた2つのブラウザプロファイルを「PC」と「スマホ」に見立てて、
GitHub API への通信をテスト側で受け止め、実際の画面操作だけで
Gist 越しの往復・オフライン中の入力・トークンが Gist に混ざらないことを確認します。

初回はブラウザの取得が必要です。

```bash
npx playwright install chromium
```
