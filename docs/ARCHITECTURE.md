# 設計メモ

## なぜこの構成か

要件は「PC と Android で使えて、同期される」でした。選択肢は3つありました。

| 案 | 長所 | 短所 | 判断 |
|---|---|---|---|
| ネイティブアプリ2本 | 各OSに最適 | 実装が2倍。企画作業に不要 | 却下 |
| クラウドSaaS前提 | 同期が楽 | 外部アカウントとサーバー費用が必要。企画内容を外部に預ける | 却下 |
| **PWA + Capacitor + 自前同期** | 1つのコードで両方。オフライン動作。データを手元に置ける | 同期を自前で書く必要 | **採用** |

企画書の内容は選考課題や社外秘を含みやすいので、既定でデータが端末内に留まり、
同期先を利用者が選べる形にしています。

## データモデル

すべてを「レコード」に正規化しています。

```ts
interface RecordBase {
  id: string;
  kind: 'project' | 'note' | 'seed' | 'tool';
  updatedAt: number;   // 単調増加するミリ秒
  deleted?: boolean;   // 墓標
}
```

- `project` — 企画のメタ情報、段階、手動チェックしたゲート
- `note` — ネタ帳の1件（`projectId: null` なら全企画共通）
- `seed` — 種の1件（4判定・★・KJ法のグループ名を持つ）
- `tool` — 思考ツール／フレームワーク／企画書。ID は `tool:<projectId>:<toolId>`

### 粒度の決め方

`note` と `seed` は件数が多く、別の端末で別々の1件を足すことがよくあるので**1件1レコード**にしました。
一方、マインドマップや企画書のような構造化データを1フィールド1レコードにすると
レコード数が爆発するので、**1企画1ツール1レコード**にしています。

この粒度なら「PCで企画書を書きながら、スマホでネタ帳に足す」は完全に両立します。
同じツールを2台で同時に編集した場合のみ、あとの保存が勝ちます。

## 同期プロトコル

```
POST /api/sync
X-Workspace-Key: <合言葉>
{ "cursor": 42, "changes": [ ...RecordBase ] }
    ↓
{ "now": 1710000000000, "cursor": 47, "changes": [ ...RecordBase ] }
```

サーバー側は各ワークスペースで単調増加する `seq` を持ち、レコードを書くたびに新しい `seq` を振ります。
クライアントは最後に受け取った `seq` を `cursor` として保持します。

### 時計に依存させない

`cursor` に時刻を使うと、端末の時計がずれたときに変更を取りこぼします。連番なら起きません。
ただし**衝突の解決**には順序の判断が要るので、そこだけ `updatedAt`（LWW）を使っています。
その代わり、時計由来の事故を2つ潰しています。

1. **時計の巻き戻し** — `lib/time.ts` の `now()` はセッション内で必ず前回より大きい値を返します。
   これがないと「あとで書いたのに古い扱いになる」編集が生まれます。
2. **端末間の時計ずれ** — 遅れた時計の端末が古い `updatedAt` で送ると push は無視されます。
   このとき勝者の `seq` がその端末の `cursor` 以下だと、通常の差分には乗りません。
   そこでサーバーは**負けた push に対する勝者を明示的に返します**（`server/src/db.js` の `rejected`）。
   これで、どの端末から見ても最終状態が一致します。

### 削除

物理削除ではなく `deleted: true` の墓標にします。物理削除だと、他端末が
「知らないレコード」として再送してしまい復活します。墓標は90日で捨てられます（`pruneTombstones`）。

## ゲートの自動判定

`domain/gates.ts` が各ゲートを評価します。`evaluate()` が

- `{ passed, detail }` を返す → 入力内容から自動判定（利用者は変更できない）
- `null` を返す → 人にしか判断できない項目なので、企画レコードのチェック状態を読む

「人に話して聞き返されたか」「一番面白い瞬間から始まっているか」は自動判定しません。
自動判定できるものだけを自動にする、という切り分けです。

## 保存

`localStorage` に JSON 1件で保存しています。テキストのみで数百KB規模を想定しているため十分です。

- 壊れた保存データでアプリが起動不能にならないよう、`load()` は失敗時に空状態を返します
- 容量超過は `QuotaError` として画面に出し、バックアップと削除を促します
- 入力のたびに全レコードを書き戻すと重いので、テキスト入力は 500ms のデバウンスと
  blur で保存します（`components/ui.tsx` の `AutoText` / `AutoInput`）

## 試験

- `server/test/sync.test.js` — 2端末の収束、ワークスペース分離、時計ずれ、壊れた入力

## 既知の制約

- 同期の衝突解決はレコード単位の LWW です。同じツールを2台で同時に編集すると片方の編集が消えます。
  文字単位でマージしたい場合は CRDT が必要ですが、1人で端末を持ち替える使い方には過剰と判断しました。
- 同期は GitHub Gist 経由です。アクセストークンは各端末の localStorage にだけ置かれます。
  ブラウザだけで動くアプリでは他に置き場所がないため、権限を `gist` のみに絞ることで
  影響範囲を限定しています。共用の PC では設定しないでください。
- 画像の添付には対応していません。テキストと数値だけを扱います。
